# 第一章：背景知识——从最近邻搜索到图索引

## 1.1 最近邻搜索：问题的定义

想象你有一个包含 **100 万个 128 维向量**的数据库——比如一百万张图片的特征向量，每条长约 128 个数字。现在你拿到一个新的查询向量 q，需要找出数据库中**与 q 距离最近的 10 个向量**。

**精确搜索**很简单：计算 q 与全部 100 万个向量的距离，取最小 10 个。数学上：

$$
\text{NN}(q, k) = \operatorname{argtopk}_{x \in \mathcal{D}} \left(-\|q - x\|_2\right)
$$

其中 $\mathcal{D}$ 是数据库。但这需要 100 万次距离计算，在 768 维向量上约需数百毫秒——远慢于实时服务要求。

**近似最近邻搜索（ANNS）**允许你返回"几乎最近"的结果，换取数量级加速。质量用 **Recall@10** 衡量：

$$
\text{Recall@10} = \frac{|\text{返回的 top-10} \cap \text{真实 top-10}|}{10}
$$

- Recall@10 = 1.0 → 完全命中
- Recall@10 = 0.9 → 9/10 命中（差一个）

**本文的质量事件最严格**：Recall@10 = **1.0**（h=10，全部 10 个命中）。这意味着必须返回与精确搜索完全相同的 top-10。

## 1.2 HNSW：分层可导航小世界图

HNSW（Hierarchical Navigable Small World）是目前最主流的 Graph-ANNS 算法。它将向量组织为一张**图**：每个向量是一个节点，节点之间有边连接（表示"在附近"）。

### 构建过程

```
输入: base 向量集合 {x₁, ..., xₙ}, 参数 M=16, efConstruction=100, 随机种子

for i = 1 to n:
    1. 给 xᵢ 分配一个层级 ℓ（受 seed 控制，指数分布）
    2. 从顶层入口贪心下降到底层，找到与 xᵢ 最近的 efC=100 个候选
    3. 将 xᵢ 连接到最近的 M=16 个候选
    4. 反向更新这些候选的邻居列表
```

**关键观察**：HNSW 构建是**顺序贪心**的——每个节点的邻居取决于之前插入的节点的图结构。因此，**插入顺序决定了图结构**。

### 搜索过程

```
输入: 查询 q, 预算 efSearch = E
输出: top-10 结果

1. 从顶层入口点开始
2. 维护候选队列（大小 = efSearch）
3. 在每层贪心搜索所有候选的邻居
4. 到达底层后，返回队列中最近的 10 个
```

**efSearch 的作用**：它控制搜索的"广度"。efSearch=10 意味着只探索 10 个候选（快但不准），efSearch=200 意味着探索 200 个候选（准但慢）。

### 为什么 efSearch 是"预算"

在搜索引擎中，efSearch 直接决定：
- **质量**：更大的 efSearch → 更多候选被考虑 → recall 更高
- **计算量**：更多的距离计算 → 延迟更高

**类比**：efSearch 就像医生看病时的检查项目数量。检查越多，诊断越准，但越贵。医生需要决定"给这个病人做多少检查"——这就是**预算决策**。

## 1.3 什么导致两个"相同"的索引不同？

给定同一批数据（如 100 万个向量），以下因素会导致构建出**结构不同**的索引：

| 因素 | 机制 | 影响 |
|---|---|---|
| **输入顺序** | 贪心构建意味着先插入的节点影响后插入节点的邻居选择 | **最大**：改变顺序=改变图结构 |
| **随机种子** | 控制层级分配的指数随机变量 | 中等（单线程下重要） |
| **线程数** | 多线程时，并行写入的顺序不确定 | 潜在（实验证实） |
| **库版本** | 不同版本的邻居选择逻辑可能不同 | 跨版本影响 |
| **硬件** | BLAS 归约顺序可能影响浮点精度 | 边缘 |

**本文的实验设计**：固定所有因素的变化方式，逐个测试每个因素的影响。

## 1.4 重建的真实部署场景

在以下常见场景中，索引会被**重建**：

1. **副本创建**：同一个服务需要多个副本以提高吞吐量
2. **自动扩缩容**：流量增长时创建新副本
3. **故障恢复**：一个副本宕机后重建
4. **蓝绿部署**：新版本上线时创建新索引
5. **库升级**：切换到新版本的 ANN 库

这些场景中，**数据和超参数相同，但构建过程不同**——这正是本文研究的"重建"。

# 第二章：核心问题的形式化

## 2.1 环境-动作模型

将每次序列化构建视为一个**环境** $E$，包含：

- 索引文件（实际存储的图结构）
- 实现（hnswlib / Faiss / Vamana）
- 构建配置（M=16, efConstruction=100）
- 插入顺序（random / lid_ascending / lid_descending）
- 种子（13 / 83 / 197 / 2029 / ...）
- 工具链（编译器版本 / BLAS / 硬件）

每个实现有自己的**有限动作集** $\mathcal{A}_E$（如 hnswlib 的 efSearch ∈ {10, 20, 40, 80, 120, 200}）。

## 2.2 失败事件与最小安全动作

对查询 q 和动作 a，定义**失败指示符**：

$$
Z_E(q, a) = \mathbf{1}\{\text{hits}(q, a) < 10\}
$$

即返回的 top-10 未能全部命中真实 top-10。

**最小安全动作**（minimum safe action）：

$$
B_E(q) = \min\{a \in \mathcal{A}_E : Z_E(q, a) = 0\}
$$

这是**让查询 q 在环境 E 上成功的最小 efSearch 值**。

**例子**（SIFT-100K 上的某个查询）：

| efSearch | 命中数 | 成功？ |
|---|---|---|
| 10 | 7 | ✗ |
| 20 | 9 | ✗ |
| 40 | 10 | ✓ |
| 80 | 10 | ✓ |
| 120 | 10 | ✓ |
| 200 | 10 | ✓ |

最小安全动作 $B_E(q) = 40$。

如果另一个构建上同一查询的结果：

| efSearch | 命中数 | 成功？ |
|---|---|---|
| 10 | 5 | ✗ |
| 20 | 8 | ✗ |
| 40 | 9 | ✗ |
| 80 | 9 | ✗ |
| 120 | 10 | ✓ |
| 200 | 10 | ✓ |

最小安全动作 $B_E(q) = 120$。

**同一个查询**，在一个构建上 efSearch=40 就够了，在另一个构建上需要 120。如果盲目迁移 efSearch=40，这个查询会失败。

## 2.3 未解决端点（⊥）

如果**所有**注册动作都不能使命中数达到 10（即使 ef=200 也不行），则 $B_E(q) = \bot$。

$\bot$ 是一个**分类符号**，不是数值——不能将其替换为"最大动作"或任何数值来"填充"。这是本文的核心语义守卫之一。

## 2.4 四结局部署语义

当我们将源构建的动作 $B_s(q)$ 部署到目标构建 $E_t$ 上时，有四种可能的结局：

| 结局 | 条件 | 损失 |
|---|---|---|
| **不安全执行** | 部署的 ef < $B_t(q)$ | recall 不达标 |
| **保守计算** | 部署的 ef ≫ $B_t(q)$ | 过多距离计算 |
| **认证回退** | 检测到不安全，切换到有安全证据的动作 | 回退成本 |
| **弃答** | 无法确定安全动作 | 服务拒绝 |

**为什么需要区分**：一个"平均 recall 掉了 5%"的索引可能对 95% 的查询毫无影响，但对 5% 的查询灾难性失败——这 5% 的用户体验完全不同于"所有查询 recall 均匀下降 5%"。四结局语义让我们精确定位损失发生在哪里。

## 2.5 增量传输风险（核心估计量）

这是本文的**主估计量**：

$$
\Delta_{s \to t} = \Pr_{q \sim P_Q}\left[Z_t(q, B_s(q)) = 1\right] - r_t^{\text{ref}}
$$

**逐项解释**：
- $Z_t(q, B_s(q)) = 1$：将源构建上查询 q 的最小安全动作部署到目标构建上，目标构建失败了
- $r_t^{\text{ref}}$：目标构建自身的基准失败率（target-bottom reference，即部署目标自身最小安全动作时的失败率）
- 差值：**迁移额外引入的失败率**，相对于"目标自己最优预算策略"的基准

**直觉**：如果 $\Delta = 0.20$，意味着"因为盲目迁移了源构建的预算，额外 20% 的查询失败了"。这个 20% 就是迁移的代价。

**置信区间**：使用 query bootstrap（5000 次重采样，seed 991），保留每次采样查询的完整有向对向量。这个区间**条件于注册构建族**——它量化的是查询分布的不确定性，而不是"未来构建"的不确定性。

# 第三章：主实验结果

## 3.1 100K 四格实验

### 实验设计

- 2 个实现（hnswlib, Faiss）× 2 个数据集（SIFT-100K, Arxiv-Nomic-100K）
- 每数据集 24 个构建：8 种子 × 3 种插入顺序（random, lid_ascending, lid_descending）
- 全部 552 个非对角有向对（源→目标）
- 750 个评估查询（与 base 和历史角色零内容重叠）
- 动作网格：hnswlib {10,20,40,80,120,200}；Faiss {16,32,64,128,256,512}
- 质量事件：h=10（全部 10 个真邻居命中）

### 结果

| 实现 | 数据集 | 有限动作变异率 | 增量传输风险 [95% CI] | 端点变异率 |
|---|---|---|---|---|
| hnswlib | SIFT-100K | 89.33% | 21.55% [20.76, 22.33] | 2.67% |
| hnswlib | Arxiv-100K | 75.87% | 17.17% [16.33, 18.06] | 2.00% |
| Faiss | SIFT-100K | 91.07% | 23.60% [22.78, 24.39] | 0.53% |
| Faiss | Arxiv-100K | 75.87% | 17.77% [16.86, 18.68] | 1.87% |

### 怎么理解这些数字

**89.33% 的有限动作变异率**意味着：在 SIFT-100K 的 750 个查询中，**89.33% 的查询在不同构建上需要不同的最小 efSearch**。只有约 10.7% 的查询在所有 24 个构建上需要完全相同的 efSearch。

**21.55% 的增量传输风险**意味着：如果你在构建 A 上校准了"这个查询用 ef=40 就够了"，然后把这个 efSearch 部署到构建 B 上，那么平均而言有 21.55% 的查询会失败——它们需要更大的 efSearch 才能达到 10/10 的命中。

**为什么这么高？** 因为 efSearch=10（最小动作）对大多数查询来说太小了。如果把 efSearch 提高到 200，几乎所有查询都能成功。但"盲目迁移"不知道这一点——它使用源构建告诉它的"最优值"，而这个值在新构建上偏低。

**端点变异率 2.67%** 意味着：只有 2.67% 的查询在某些构建上完全无法成功（即使 ef=200）。这证明主要变异来自**有限动作之间的切换**，不是端点不可达。

# 第四章 Theorem 1：不可迁移下界

## 4.1 数学陈述与证明

### 定理陈述

设两个构建环境 $E_0, E_1$，策略观察转录 $T \sim P_i^T$ 并输出动作。令 $D_i$ 为环境 $E_i$ 中"可接受"的动作区域，$D_0 \cap D_1 = \varnothing$，错误动作损失 $\ge \Delta$。则：

$$
\max_{i \in \{0,1\}} \mathbb{E}[\ell_i] \ge \frac{\Delta}{2}(1 - \text{TV}(P_0^T, P_1^T))
$$

### 证明（逐步推导）

**第一步**：定义二值决策函数。

对每个转录 $T$，定义决策规则 $I(T)$：
- 如果输出的动作在 $D_0$ 中，$I(T) = 0$
- 如果输出的动作在 $D_1$ 中，$I(T) = 1$
- 否则任意分配

由于 $D_0 \cap D_1 = \varnothing$，动作不在 $D_0$ 中就在 $D_1$ 中（或都不在，此时损失也为 $\ge \Delta$）。

**第二步**：计算每个环境的期望损失。

在环境 $E_0$ 下：如果策略选择了一个在 $D_1$ 中的动作，这个动作在 $D_0$ 的约束下不可接受，损失 $\ge \Delta$。类似地，在 $E_1$ 下选择 $D_0$ 中的动作损失 $\ge \Delta$。

总损失：
$$
\mathbb{E}_0[\ell_0] + \mathbb{E}_1[\ell_1] \ge \Delta \cdot \{P_0[I=1] + P_1[I=0]\}
$$

**第三步**：连接到 TV。

两环境上的最小检验错误和：
$$
P_0[I=1] + P_1[I=0] \ge 1 - \text{TV}(P_0^T, P_1^T)
$$

这是 Bretagnolle–Huber 不等式的直接推论。

**第四步**：取最大值。

$$
\max_i \mathbb{E}[\ell_i] \ge \frac{1}{2}(\mathbb{E}_0[\ell_0] + \mathbb{E}_1[\ell_1]) \ge \frac{\Delta}{2}(1 - \text{TV})
$$

∎

### 直觉解释

想象你是一个运维工程师，管理两个索引副本。你知道查询 q 在副本 A 上需要 efSearch=40，但你不知道现在服务的是副本 A 还是副本 B。如果副本 B 上 q 需要 efSearch=120，而你部署了 40，这个查询就失败了。

**定理 1 告诉我们**：如果这两个副本在探测信息上"看起来一样"（TV 小），你**无法避免**某些查询失败——除非你把 efSearch 开到足够大（但这会浪费计算）。这就是"不可迁移性"的数学含义。

## 4.2 Theorem 1 前提的实证检验

### 我们测量了什么？

定理 1 需要**两个前提**：

1. **TV 小**：探测转录无法区分两个构建
2. **区域不相交**：两个构建需要不同的（且互斥的）动作

### TV 的测量

**方法**：训练一个强分类器（HistGradientBoosting），输入为每个查询在 k 个最便宜动作上的命中数向量，输出为"属于构建 s 还是构建 t"。如果分类器准确率接近 50%（随机），则 TV 接近 0。

**结果**：在全部 552 个有向对上，k ∈ {1,3,6}：
- **命中率转录**：分类器准确率 0.49–0.51（纯随机）→ TV ≤ 0.25
- **运行时特征**（visited nodes, 队列统计, 延迟）：准确率 0.56–0.58，最差对 0.72 → TV ≥ 0.44

**诚实结论**：命中数转录不可区分（前提成立），但运行时特征部分可区分（前提在此类中弱化）。

### 为什么运行时特征也给了 0.72？

因为它们是 (q, build) 的**联合函数**——每个查询在每个构建上有不同的 visited count。所以它们确实可以区分构建。但重要的是：**即使区分了构建，你也不知道应该用多大的 efSearch**——因为最小安全动作是 build-structure-dominated 的。

### 置信上界的推导

对于有限支持上的离散分布，经验 TV 收敛于真 TV。DKW 不等式给出：

$$
\text{TV} \le \widehat{\text{TV}} + \sqrt{\frac{2S \log(2/\delta)}{n}}
$$

其中 S 是有效支持大小，n 是每分布的样本数。以 S_eff ≈ 30（实际承载概率的结果数）和 n = 375：

$$
\text{TV} \le 0.25 + 0.14 = 0.39 \quad (95\% \text{ confidence})
$$

因此：Theorem 1 的损失下界 = $\frac{\Delta}{2}(1-0.39) = 0.305\Delta$——在这个置信上界下仍然是非零的。

# 第五章 Theorem 2：条件可恢复性

## 5.1 直觉

Theorem 2 说：如果你有一个命名目标构建，一个冻结的动作族，以及独立的目标证据，你可以**认证**一个动作——但需要五个条件同时满足。

这就像药品审批：你需要证明药物有效（条件 i）、可以做对照实验（条件 ii）、有安全余量（条件 iii）、实验设计无偏（条件 iv）、以及有备用方案（条件 v）。

## 5.2 五条件的逐 target 审计

我们在 48 个目标上逐一检查了这五个条件：

| 条件 | 状态 | 解释 |
|---|---|---|
| (i) 端点可行 | ✅ 满足 | 最大动作风险 ≤ δ−2γ |
| (ii) 可辨识 | ✅ 满足 | 选择数据可区分动作 |
| (iii) **正 margin** | ❌ **全部失败** | 非最大动作的风险都在 margin 带内 |
| (iv) 独立角色 | ✅ 满足 | 375/94/281 不相交 |
| (v) 有效回退 | ✅ 满足 | 最大动作或弃权 |

**γ 敏感性分析**：
- γ=0.005（margin 需求 4%）：16/24 和 21/24 个目标有 margin 动作
- γ=0.01：16/24 和 8/24
- γ=0.02：0/24（全无）

**核心发现**：不是"margin 不存在"，而是"margin-band 动作（风险 2.5–4%）在 m=59 零失败认证下通过率太低"。用完整的 CP 检验（允许非零失败），这些动作在 m=289–1149 时可以通过。

**对论文表述的影响**：不能说"margin 系统性缺失"，应该说"认证功效在本注册样本量下绑定"。

# 第六章 Theorem 3：保形池化

## 6.1 直觉

想象你有 22 个历史构建的标签缓存。对于每个查询 q，你知道它在每个历史构建上需要多大的 efSearch。

**池化策略**：取这 22 个值的最大值，作为部署动作。直觉是"如果 22 个副本中任何一个需要更大的预算，那我就准备更大的预算"。

**为什么这样安全？** 因为如果新构建与历史构建来自同一个生成过程（可交换），那么新构建的预算需求"不太可能超过所有 22 个历史构建的最大值"。

**Theorem 3 用数学精确化了这一点**：通过秩均匀性论证，超越概率 ≤ 1/(k+1)... 但这不是简单的 1/(k+1)——通过精心选择部署动作（第 m 阶统计量），我们可以将超越概率控制在 α 以内。

## 6.2 Theorem 3 的正式陈述

设 $B_{E_1}(q), \ldots, B_{E_k}(q), B_{E_t}(q)$ 跨构建可交换。令 $m = \lceil(1-\alpha)(k+1)\rceil$，部署：

$$
a(q) = \text{第 } m \text{ 小的 } \{B_{E_1}(q), \ldots, B_{E_k}(q)\}
$$

则：
$$
\Pr[B_{E_t}(q) > a(q)] \le \alpha
$$

**证明**：
1. 可交换性 ⟹ 目标的 B 在 k+1 个值中的秩均匀分布于 {1,...,k+1}
2. 部署失败事件 = {目标的 B > 第 m 小} = {目标的秩 > m}
3. $P(\text{rank} > m) = \frac{k+1-m}{k+1} \le \frac{k+1 - \lceil(1-\alpha)(k+1)\rceil}{k+1} \le \alpha$

关键是第三个不等号：$k+1-m \le \alpha(k+1)$ 由 $m \ge (1-\alpha)(k+1)$ 保证。

## 6.3 实测验证

在 24 个注册构建上，k=23（留一法），α=0.05：

| 指标 | SIFT-100K | Arxiv-100K |
|---|---|---|
| 实测失败率 | 0.96% | 1.35% |
| 名义 α | 5% | 5% |
| 证书有效性 | ✅ 0.96% ≤ 5% | ✅ 1.35% ≤ 5% |
| DistComp vs oracle | 1.44× | 1.32× |
| 弃权率 | 2.4% | 2.7% |

**远低于名义 α=5%**——证书在实践中是保守的。

## 6.4 k-阶梯（源需求随规模增长）

| 规模 | k=3 | k=5 | k=7 | k=10 | k=22 |
|---|---|---|---|---|---|
| SIFT-100K | 7.6% | 3.3% | — | 1.2% | 0.96% |
| SIFT-1M | — | — | 10.4% | — | — |
| deep-10M | 26.8% | — | 23.3% | — | — |

**关键发现**：池化的源需求**随规模增长**。在 100K 时 22 个源足够（风险 <1%），但在 10M 时 7 个源仍留下 23.3% 的风险。这意味着池化不是万能的——规模越大，需要保留的历史副本越多。

# 第七章 执行安全桥

## 7.1 问题

Theorem 3 保证的是**标签覆盖**：

$$
P[B_t(q) > a(q)] \le \alpha
$$

但部署安全需要：

$$
P[Z_t(q, a(q)) = 1] \le \delta
$$

从标签覆盖到执行安全需要一个条件：**部署的 action ≥ B_t(q) 时必成功**（即后缀单调性）。

## 7.2 ν 的测量

我们穷举检查了全部 (query, build, ef ≥ B_point) 三元组：

| 数据集 | ν（非单调违规率） | 三元组数 |
|---|---|---|
| hnswlib SIFT-100K | **0.0** | ~4.4M |
| hnswlib Arxiv-100K | **0.0** | ~4.4M |
| Vamana SIFT | **0.0** | 27,000 |
| Vamana Arxiv | **0.0** | 27,000 |
| 1M | **0.0** | 14,655 |
| 10M | **0.0** | 11,144 |
| GloVe-100 | **0.0** | 9,003 |

**结论**：在所有注册网格上，部署 ≥ B_t(q) 的动作必成功。执行失败 = α + ν = α + 0 = α。

## 7.3 诚实声明

ν=0 是在注册网格上穷举检查的结果。它不能自动推广到未来构建——新的构建过程可能产生非单调行为。但至少在我们测试的所有配置中，这个桥是完美的。

# 第八章 分层保形池化（TCP）算法

## 8.1 算法流程

### 离线阶段（每个副本一次性）

```python
# 输入: k 个历史构建的索引, 评估查询集 Q
for each build E_i:
    for each query q ∈ Q:
        for each ef ∈ {10, 20, 40, 80, 120, 200}:
            result = search(q, E_i, ef)
            hits = |result ∩ truth(q)|
        B_i[q] = min{ef : hits ≥ 10}
# 缓存 {q → [B_1(q), ..., B_k(q)]}
```

### 在线阶段

```python
# 输入: 新查询 q
if q in cache:  # 重复查询
    vals = sorted([B_1(q), ..., B_k(q)])
    a = vals[ceil((1-α)(k+1)) - 1]  # (1-α)-分位数
    deploy ef = a
else:  # 冷查询
    deploy ef = max_registered_action  # 或弃答
```

## 8.2 为什么这是"认证"的？

关键在于**秩均匀性**：由于可交换性，新构建的 B_t(q) 在 k+1 个值中的秩是均匀的。因此，部署第 m 小值时：

$$
P[B_t(q) > a(q)] = P[\text{rank}(B_t) > m] \le \frac{k+1-m}{k+1} \le \alpha
$$

这不是概率近似——这是**精确的有限样本保证**，只要可交换性成立。

## 8.3 实测效果总结

| 指标 | 数值 | 说明 |
|---|---|---|
| 风险（100K） | 0.09–0.18% | 远低于 δ=5% |
| 风险（10M） | 23.3% @ k=7 | 规模退化确认 |
| DistComp | 1.32–1.45× oracle | 省 3.5× vs always-max |
| 延迟 p95 | 274 µs | 与 always-max 不可区分 |
| 弃权率 | 2.4–2.7% | 安全保留 |
| 证书状态 | **有限样本、无真值** | 需 k≥1/α−1 个缓存构建 |

# 第九章 种群农场

## 9.1 为什么需要 farm？

所有正式实验都使用 24 个注册构建——但审稿人会问："24 个构建能代表未来的所有重建吗？"种群农场通过生成 **200 个独立构建**来回答这个问题。

## 9.2 设计

| 参数 | SIFT-10K farm | Arxiv-10K farm |
|---|---|---|
| base | train[:10000] | train[:10000] |
| 构建 | 2 臂 × 100 | 2 臂 × 100 |
| 臂 A | 单线程，随机 seed + order | 同左 |
| 臂 B | 8 线程，随机 order，无 seed 控制 | 同左 |
| 查询 | test 的 500 个预注册子集 | 同左 |
| forensics | overlap = 0 | 同左 |

## 9.3 结果

| 指标 | SIFT-10K | Arxiv-10K |
|---|---|---|
| 有向对风险均值 | 23.4% / 23.5%（双臂） | 21.6% / 21.6%（双臂） |
| p95 | 26.6% / 26.8% | 24.6% / 24.8% |
| max | 31.4% / 31.2% | 29.6% / 30.4% |
| **超 2% gate 比例** | **100%** | **100%** |
| 两臂差异 | 不可区分 | 不可区分 |
| KS 秩均匀性 | 0.114 / 0.120 | 0.120 / 0.113 |

**关键发现**：
1. **双数据族确认**：SIFT 和 Arxiv 农场均显示 100% 对超 gate
2. **可交换性跨数据族成立**：两个 farm 的 KS 统计量一致
3. **8 线程不放大风险**：两臂不可区分

## 9.4 一个关键警告

农场在 10K base 上运行——10K 的索引质量本身较低（max ef 下 recall 仍 ~85%）。farm 结果不能直接外推到 100K 或 1M 规模。它的价值是**检验可交换性前提**，不是估计绝对风险。

# 第十章 完整决策规则

## 10.1 五层代价排序决策规则

```
给定: 新重建的索引 E_t, 历史构建池, 风险容忍 δ, 预算

层 1: 确定性合同
  条件: 可以控制重建过程（固定顺序+seed+单线程+工具链）
  动作: 按 E_s 的标定预算部署
  保证: 风险增量 = 0（字节一致）; 绝对风险 = 源策略的绝对风险
  代价: 构建 1.71–3.52×

层 2: 目标重画像 (M5')
  条件: 真值可计算（暴力搜索可行）
  动作: 逐查询校准目标最小安全预算
  保证: 风险 = 端点质量 (~0.8–1.3%)
  代价: 真值计算 0.05–5s + 每查询 oracle 代价

层 3: 保形池化 (Thm 3)
  条件: 有 k ≥ 1/α−1 个历史构建的缓存标签
  动作: 部署 (1−α)-分位数动作
  保证: 有限样本, ≤α（需可交换性 + ν=0）
  代价: 1.32–1.44× oracle; 10M 处退化

层 4: 冻结动作认证 (Thm 2)
  条件: 有独立认证查询
  动作: 筛选 + CP 认证
  保证: 安全或弃答（安全保证）
  边界: 本网格上只有最大预算可认证

层 5: 弃答
  条件: 以上全不可行
  动作: 拒绝服务
  保证: 安全保留
```

## 10.2 使用指南

| 场景 | 推荐层 | 理由 |
|---|---|---|
| 可以控制重建过程 | 层 1 | 唯一零风险路线 |
| 不能控制重建 + 真值便宜 | 层 2 | 1.00× oracle，最优 |
| 不能控制重建 + 有历史缓存 | 层 3 | 1.32–1.44×，认证 ≤α |
| 不能控制重建 + 无历史 | 层 5 | 最大动作 0.8–1.3%（不确定全） |
| 想要认证但 margin 不足 | 层 5 | CP 功效不足以认证非最大动作 |
